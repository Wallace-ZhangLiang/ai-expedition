# Triton 原理入门：块思维、三大原语、完整旅程

> **定位**：跑通第一个 Triton kernel 后，回头搞懂那几行代码在干嘛，打好地基再进真实 kernel。

## 〇、一句话

**Triton 不是写「怎么算」，而是写「怎么分块算」**——你只负责把数据切成块、声明每块读什么写什么，剩下怎么并行、怎么调度，编译器搞定。

## 一、块（tile/block）思维：工作分片

一个 kernel 不是一次处理 1 个元素，而是**切成很多块**，每块 `BLOCK_SIZE` 个元素，一个块一个程序实例。

```
你不是一个人干完全部 1024 个元素，
而是切成 4 块、每块 256 个，4 个「工人」一人扛一块
```

| 代码 | 意思 | 比喻 |
|---|---|---|
| `grid = (4,)` | 一共开 4 个工人（块） | 4 个工位 |
| `pid = tl.program_id(0)` | 「我是第几号工人？」 | 工牌号 |
| `offsets = pid*BLOCK + tl.arange(0,BLOCK)` | 我负责哪片元素 | 我的工位管哪片区域 |
| `mask = offsets < n` | 别超了元素总数 | 边界护栏 |

> **关键直觉**：性能起点在「块切得好不好」——块太大浪费算力，块太小调度开销大。看真实 kernel 时，`BLOCK_SIZE` 怎么取是第一件要留意的事。

## 二、三大原语：工人的工具

| 原语 | 作用 | 比喻 |
|---|---|---|
| `tl.program_id(axis=0)` | 我是第几块 | 编号 |
| `tl.arange(0, BLOCK)` | 我这一块管哪些下标 | 编号范围 |
| `tl.load(ptr+offsets, mask)` | 从内存读**一整块** | 一趟卡车拉一车货 |
| `tl.store(ptr+offsets, value, mask)` | 写**一整块**回内存 | 卸货 |
| `tl.dot(a, b)` | 矩阵乘法（GEMM 用） | 算 W·x |

**最反直觉的一点**：Triton 里**没有显式的 for 循环**。所有原语都是「一整块一起处理」，编译器负责把块并行化。这和普通 Python 是两套思维，要刻意切换。

## 三、完整旅程：一段代码怎么变成结果

```
你的 add_kernel[grid](x, y, out, ...)
      ↓  Triton 前端：Python 代码 → IR（中间表示，跟硬件无关）
      ↓  某硬件后端：IR → 该硬件能跑的指令
      ↓  硬件执行：多个块并行跑，结果写回 out
```

> 这段旅程就是「为什么有的 kernel 在某硬件上跑不了/慢」的根因——中间某个环节（某个 Triton 语法该后端还不支持）卡住了。

## 四、意义

1. **归因**：每个「跑不通」的 kernel，本质都是「完整旅程」里某一段卡住。归因时先定位是哪一段（前端语法？后端不支持？性能差）。
2. **读代码**：vLLM 等框架里的真实 kernel，不管多复杂，拆开都是「分块 + load/store/dot」的组合。块思维是阅读的钥匙。
3. **调性能**：`BLOCK_SIZE` 等切块参数是性能调优的第一手调节旋钮。

## 五、动手练习（可选，加深理解）

在跑通的 demo 基础上改三处，每处跑一次看结果对不对：

1. `BLOCK_SIZE` 改成 128（或 64）——结果应仍正确（块切细了而已）
2. 改 `n` 为 1000（不是 256 的整数倍）——**mask 发挥作用**，不会越界报错
3. 把 `x + y` 改成 `x * y`——换成乘法验证你真的看懂了

改完能跑通，说明块思维 + mask 你已经吃透了。
