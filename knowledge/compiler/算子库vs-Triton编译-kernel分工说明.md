# 算子库 vs Triton 编译：哪些 kernel 走哪条路

> **定位**：讲清「哪些 kernel 走 Triton 编译、哪些走算子库」这条分工，适合无底层背景时快速建立心智。

## 一、先搞懂「kernel」是什么

一个模型跑起来，拆开看就是**无数个小计算单元**在挨个执行，每个小计算单元就叫一个 **kernel（内核/算子）**。

最典型的例子——**矩阵乘法（GEMM）**：

```
y = W·x + b
```

这就是一个 kernel。还有注意力（Attention）、归一化（LayerNorm）、激活函数（ReLU）…… 每个都是独立 kernel。

**关键点**：这些 kernel 都是「写给人看的代码」，加速卡（NPU/GPU）不认识。要让它跑起来，必须翻译成硬件能执行的指令。**翻译方式有两条路。**

## 二、两条路：算子库 vs Triton 编译

### 路 A：算子库

> **预制菜 / 大厨招牌菜**：厨房里已备好一批做好的菜，点单直接端上桌。

昇腾的 **CANN 算子库**（NVIDIA 对应 cuBLAS/cuDNN 等）里，预先存了一批**人工调优好、预编译好**的常用算子：矩阵乘 GEMM、卷积、归一化、注意力基础版、激活函数……

- ✅ 打开就能用，性能最好（专家反复调过）
- ✅ 稳定可靠
- ❌ **覆盖有限**——只覆盖「常见、通用」的算子，新出的、小众的没有

### 路 B：Triton 编译

> **现场照着菜谱现做**：点什么，厨师现场按菜谱翻译、现炒。

**Triton 编译** = 拿到 Triton 写的 kernel 源码，编译器**现场翻译**成硬件指令：用户（或 torch.compile）写好 Triton 代码 → Triton 前端解析 → 硬件后端翻译 → 生成可执行代码。

- ✅ **什么都能做**——不管多新多怪的 kernel，只要有源码就能翻译
- ❌ 性能取决于编译器翻译得好不好，通常**不如人工调优的算子库**
- ❌ 要现场编译，有编译时间开销

## 三、对比

| | 算子库 | Triton 编译 |
|---|---|---|
| 比喻 | 预制菜/招牌菜 | 现场按菜谱做 |
| 谁写的 | 人工预调优 | 编译器自动翻译 |
| 覆盖 | 常见通用算子 | 任意新 kernel |
| 性能 | 最好 | 取决于编译器质量 |
| 典型场景 | 矩阵乘、卷积、归一化 | 各种新 attention 变体、MoE、量化 kernel |

## 四、放到实际模型里看

一个模型跑起来，**两类算子混着走**：

```
一个 LLM 推理：

  W·x 矩阵乘法        → 算子库（有高度优化的 GEMM）
  激活函数 GeLU       → 算子库
  LayerNorm           → 算子库（或 torch.compile 生成的 Triton 融合版）

  新型 Attention（如 GQA）→ 算子库没有 → 只能走 Triton 编译
  MoE 专家路由        → 算子库没有 → Triton 编译
  KV cache 读写       → 算子库没有 → Triton 编译
  量化 kernel         → 算子库没有 → Triton 编译
```

**关键**：新模型带来的麻烦，几乎全在「算子库没有的那部分」——也就是 **Triton 编译这条路上**。

## 五、「分工」到底在问什么

「哪些走 Triton 编译、哪些走算子库」实际在问三层：

1. **覆盖层**：算子库里到底有哪些？（库里有的，就不需要自己管）
2. **派发层**：遇到一个计算，到底调谁？（`torch.matmul` 走 torch 派发到算子库，还是被 torch.compile 生成 Triton 代码？）
3. **冲突层**：两边都能做时选谁？（对比性能与稳定性，定规则，避免重复投入）

**简单判断**：

| 情况 | 走哪条路 |
|---|---|
| 算子库有现成的，性能够好 | 算子库 |
| 算子库没有（新 kernel） | Triton 编译 |
| 两边都有 | 对比性能，定规则，避免重复 |

## 六、意义

分工确认清楚后，工作边界就清晰了：

- **算子库覆盖范围内的** → 不在 Triton 的工作范围内
- **要走 Triton 编译的** → Triton 的主场：能不能编译、能不能跑通、性能差距多少、怎么推动上游改进
